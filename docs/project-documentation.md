# National Care Approval Flow Documentation

National Care Approval Flow is a React/Vite workspace for assigning, reviewing, approving, scheduling, and reporting creative work. It supports custom task workflows, role-based review queues, shared persistence through Neon or Google Drive, local offline mode, deadline reminders, daily reports, member administration, and campaign publishing schedules.

The application is designed around a single workspace state that contains tasks, notifications, settings, members, workflow definitions, and daily reports. The browser can run entirely from local IndexedDB, or it can synchronize the same state through server APIs backed by Neon Postgres. Google Drive can also be used as shared file and metadata storage for deployments that need Drive-based task folders.

## Technology Stack

- React 19 with TypeScript for the user interface.
- Vite 6 for development, builds, and Vercel serverless function integration.
- Tailwind CSS 4 for styling.
- Lucide React for icons.
- Neon serverless Postgres for shared application state when `VITE_USE_NEON_DATA=true`.
- Supabase profile/auth integration for workspace identity checks when configured.
- Google Drive and Google Picker APIs for shared task folders, uploads, previews, and metadata when `VITE_USE_SHARED_DRIVE_DATA=true`.
- IndexedDB for local-only state and offline usage.
- Node's built-in test runner through `tsx --test`.

## Core Domain Model

The central domain types live in `src/lib/types.ts`.

### Users and Roles

Users can have one of these roles:

- `team_member`
- `reviewer`
- `art_director`
- `team_leader`
- `manager`
- `developer`
- `marketing_manager`
- `admin`

Roles drive visibility, task ownership, review actions, settings access, daily report access, and workflow-management permissions. Some permission groups are configured through `AppSettings`, including settings managers, assignment creators, senior reviewers, contributors who can or cannot self-assign, and reporting relationships.

### Tasks

A task contains:

- identity fields such as `id`, `code`, `name`, `description`, and `taskType`;
- workflow routing fields such as `workflowId`, `workflowSnapshot`, `workflowActivePhaseIds`, `workflowCurrentPhaseId`, approvals, skipped phases, and phase history;
- ownership fields such as `createdBy`, `handledBy`, `currentOwnerRole`, `currentOwnerUserId`, and `currentOwnerUserIds`;
- scheduling fields such as `deadlineAt`, `scheduledPublishAt`, `publishedAt`, and reminder receipts;
- files and versions through `TaskVersion` and `UploadedTaskFile`;
- comments, audit events, active work sessions, assignment links, and daily-report metadata.

The workflow snapshot is copied into the task at assignment time. That keeps an in-progress task stable even when admins later edit global workflow definitions.

### Workflows

Workflows are configured with `WorkflowDefinition` and `WorkflowPhaseDefinition`.

A phase can represent:

- work;
- content review;
- first review;
- final review;
- a decision node;
- a note or section node for builder layout.

Workflow phases support sequential and parallel execution, explicit graph edges, delay days, skip rules, required approvals, revision limits, parent/child relationships, owner roles, explicit users, responsibility IDs, deliverables, and return/pass/fail routing.

The workflow engine is split across:

- `src/lib/workflowUtils.ts` for owner resolution, status mapping, access helpers, phase availability, and skip-rule evaluation.
- `src/lib/workflowRuntime.ts` for initialization, advancement, return routing, handoff planning, and graph traversal.
- `src/lib/workflowGraph.ts` for graph validation, entry phases, downstream checks, and explicit edge utilities.
- `src/lib/workflowAssignment.ts` and `server/workflowAssignment.ts` for assignment-time validation and owner preparation.
- `src/lib/workflowOmissions.ts` and `server/workflowOmissions.ts` for optional phase omission rules.

### App Settings

`AppSettings` stores workspace-level configuration:

- responsibilities and custom permissions;
- manual users and deleted-member tombstones;
- priority definitions;
- business calendar and custom working hours;
- workflow definitions and task-type mappings;
- assignment and contributor permission groups;
- first/final reviewer lists;
- campaign platforms;
- daily report scheduling and receivers;
- reporting-senior mappings;
- migration markers.

Defaults and merge logic live in `src/lib/appSettings.ts`.

### Notifications

Notifications are in-app records tied to a user and optionally a task or daily report. The app projects notifications at read time so users only see notices they are still allowed to see. Deadline and report notifications also re-check current audience rules, which prevents stale notices from leaking after reassignment, membership changes, or deadline edits.

## Main User Flows

### Authentication

The app supports configured workspace accounts and server-backed workspace sessions.

In local mode, users can sign in with the configured workspace accounts. In Neon/shared mode, `api/app-state.ts` uses `server/workspaceAuth.ts` to authenticate users through either:

- an HttpOnly workspace cookie created by manual password login; or
- a Supabase bearer token, with profile lookup through the configured Supabase REST API.

Private fields such as password hashes are stripped from settings before returning state to the browser.

### Dashboard and Queues

`src/App.tsx` routes to views using query parameters:

- dashboard overview;
- performance dashboard;
- notifications;
- create/upload task;
- assigned work;
- assigned tasks;
- campaign scheduler;
- deadline calendar;
- daily reports;
- user management;
- settings;
- workflow builder;
- review queues;
- due-today and due-this-week queues;
- archived tasks;
- task detail.

Task visibility is filtered through `canViewTask` from `src/lib/taskPolicy.ts`, so each route receives only work the current user is permitted to inspect.

### Task Creation and Assignment

Task creation starts in `src/components/CreateTask.tsx` and flows through the app store in `src/lib/store.tsx`.

At creation time the app:

1. Resolves the selected task type to a workflow.
2. Clones the workflow into the task snapshot.
3. Applies content-review choices and optional skipped phases.
4. Validates that required workflow owners are assigned.
5. Initializes active workflow phases.
6. Creates notifications for the first responsible owners.
7. Persists the state through the active storage adapter.

Work assignments are a related flow used to assign work for a day, week, or month. Assigned workers can upload deliverables, which are converted into task versions and routed to the next workflow step.

### Review and Approval

Review actions are handled through task detail and the store. Workflow-aware tasks advance through `approveWorkflowPhase`, `rejectWorkflowPhase`, `skipWorkflowPhase`, and related runtime helpers.

Review phases can:

- approve and move forward;
- request changes and return to a previous phase;
- route through decision nodes;
- wait for multiple approvals;
- split into parallel phases;
- respect delayed handoffs;
- freeze the final art director assigned at task creation.

Legacy review modes such as `full_review`, `quick_look`, and `direct_to_ad` remain supported and are normalized into the current workflow model where possible.

### Comments, Versions, and Files

Each task can contain multiple versions. Versions store uploaded files, previews, submitter IDs, and submission notes. Comments can include text and image sections, edit history, deletion metadata, and audit-style system actions.

File handling differs by persistence mode:

- Local mode keeps file blobs and previews in browser state where possible.
- Drive mode uploads originals and preview images to the selected Drive root.
- Neon mode persists metadata through the app state API; file support depends on linked URLs and browser/Drive upload paths used by the task.

Supported upload extensions are defined in `src/lib/uploadLimits.ts` and currently include `png`, `jpg`, `jpeg`, `mp4`, and `pdf`. The default upload limit is 50 MB, controlled by `VITE_MAX_UPLOAD_MB`.

### Campaign Scheduling

Campaign and media-buying tasks can store a scheduled publish time, platform, budget fields, and publish notes. `src/components/CampaignScheduler.tsx` exposes month, overdue, upcoming, and published views. The app can mark publish reminders while the browser is open, and scheduled campaign metadata is part of the task record.

### Deadline Calendar and Reminders

Deadlines are represented by `deadlineAt` ISO timestamps. New deadline input is interpreted in the Africa/Cairo timezone. Legacy date-only deadlines are treated as 23:59 Cairo time on that date.

Deadline logic is implemented in:

- `src/lib/deadlineUtils.ts` for due-today and due-this-week filters.
- `src/lib/deadlinePolicy.ts` for parsing, audience selection, notification projection, reminder planning, and receipt preservation.
- `api/cron/deadline-reminders.ts` for unattended server-side reminder execution.

The cron endpoint sends two stages of reminders:

- within 24 hours, while more than one hour remains;
- within one hour.

Delivery is keyed by task, deadline timestamp, stage, and recipient, so repeated cron runs do not duplicate notices.

See `docs/deadline-scheduler-deployment.md` for activation details.

### Daily Reports

Daily reports combine automatic work evidence with manual notes. They are modeled by `DailyReport`, `DailyReportEntry`, and edit-history records.

The planner in `src/lib/dailyReportScheduler.ts` and work-entry builder in `src/lib/dailyReportWork.ts` can:

- prepare report reminders near the configured end-of-day time;
- create private draft reports;
- collect active work sessions, uploads, and review actions;
- preserve manual edits;
- submit nonempty reports to configured receivers and reporting seniors.

Report visibility and notification projection live in `src/lib/reportPolicy.ts` and `server/reportAccess.ts`.

### User and Member Management

Admins and configured managers can manage member profiles, responsibilities, reporting relationships, and deleted-member records.

Deleted members are stored as tombstones rather than removed silently. Local mode stores tombstones in IndexedDB. Neon mode also stores them in the `deleted_member_tombstones` table. This prevents deleted members from returning when older clients sync stale settings.

Member deletion is blocked if the removed user still owns unfinished work. The blocker detection is shared between client and server logic.

### Workflow Builder

`src/components/WorkflowBuilderPage.tsx` and related workflow utilities let managers configure workflows, task types, owners, review styles, optional steps, decision routing, and graph layout.

Workflow deletion is also tombstoned in Neon through `deleted_workflow_tombstones`, so old clients cannot restore deleted workflows by saving an older workspace state.

## Persistence Modes

The app chooses a persistence mode from environment flags and runtime readiness.

### Local IndexedDB

Local mode is the fallback and is useful for offline operation. State is stored in the `national-care-approval-flow` IndexedDB database under the `app_state` object store.

Local state includes:

- tasks;
- notifications;
- settings;
- daily reports;
- deleted-member tombstones;
- notification reset records.

### Neon Shared State

When `VITE_USE_NEON_DATA=true`, the browser uses the server API backed by Neon. The primary endpoint is `api/app-state.ts`.

The API stores a single JSON state row in `app_state`:

```sql
CREATE TABLE IF NOT EXISTS app_state (
  id text PRIMARY KEY,
  state jsonb NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

It also creates tombstone tables:

```sql
CREATE TABLE IF NOT EXISTS deleted_member_tombstones (
  member_id text PRIMARY KEY,
  record jsonb NOT NULL
);

CREATE TABLE IF NOT EXISTS deleted_workflow_tombstones (
  workflow_id text PRIMARY KEY,
  deleted_at timestamptz NOT NULL DEFAULT now()
);
```

Server writes are guarded by authentication, same-origin checks for cookie-authenticated writes, access-aware task/report merge logic, and optimistic revision checks for sensitive operations.

### Google Drive Shared Storage

When `VITE_USE_SHARED_DRIVE_DATA=true`, the app can connect to Google Drive, select a shared root folder, import Drive files as tasks, and store task metadata/files in Drive.

Drive logic lives in:

- `src/lib/driveAuth.ts` for OAuth token handling, picker loading, selected root storage, and Drive connection status.
- `src/lib/driveDb.ts` for Drive file/folder operations, metadata JSON, task import, uploads, notifications, and settings.
- `api/drive/resumable-upload.ts` for resumable upload support.

Drive mode requires a Google OAuth web client, API key, app ID, and enabled Drive and Picker APIs.

## API Endpoints

### `GET /api/app-state`

Returns the current shared state filtered for the authenticated viewer. Query flags:

- `?meta=1` returns only the current update timestamp.
- `?settings=1` returns public settings.
- `?auth=session` returns the current workspace session.

### `PUT /api/app-state`

Writes a new state snapshot. The server merges only changes the actor is authorized to make, preserves private settings, merges authorized reports, validates task access, blocks unsafe member deletion, applies deadline receipt preservation, and writes tombstones.

### `POST /api/app-state?auth=login`

Authenticates a manual workspace user and returns an HttpOnly session cookie.

### `POST /api/app-state?auth=logout`

Clears the workspace session cookie.

### `GET /api/metadata`

Fetches permitted link metadata for task attachment previews. Authorization is delegated to `server/taskMetadata.ts`.

### `GET` or `POST /api/cron/deadline-reminders`

Runs deadline reminder and daily report planning against Neon. Requires `Authorization: Bearer <CRON_SECRET>` when configured for production use.

### `api/drive/resumable-upload`

Supports Drive resumable uploads from the app.

## Security and Access Controls

The project includes several layers of access control:

- Client-side route and action gating through policy functions.
- Server-side task visibility and merge validation in `server/taskAccess.ts`.
- Server-side report visibility and merge validation in `server/reportAccess.ts`.
- Same-origin checks for cookie-authenticated state writes.
- HttpOnly, signed workspace session cookies for manual users.
- Private settings stripping before returning state.
- Deleted-member tombstones to prevent stale clients from restoring removed users.
- Deleted-workflow tombstones to prevent stale clients from restoring removed workflows.
- Deadline and report notification projection at read time.
- Member-deletion blockers for unfinished assigned work.

The server API is the source of truth in Neon mode. Client-side checks improve UX, but server validation protects shared state.

## Data Migration and Recovery Notes

- The app can detect local-only items when shared persistence is active and offers to move them into shared data.
- The error boundary can clear local cache if old browser data prevents the app from loading.
- Notification reset records remove stale legacy notifications without repeatedly reintroducing them.
- Member tombstones are kept separately from normal settings to survive stale client saves.
- Workflow tombstones are applied to settings on every Neon read/write.

## Common Maintenance Tasks

### Add or Change a Role Permission

1. Update the relevant policy in `src/lib/*Policy.ts`, `src/lib/workflowUtils.ts`, or `src/lib/workAssignmentUtils.ts`.
2. Mirror server enforcement in `server/taskAccess.ts`, `server/reportAccess.ts`, or the applicable server validator.
3. Add or update tests that prove the permission both allows the intended action and blocks unauthorized users.

### Add a Workflow Feature

1. Extend `WorkflowPhaseDefinition` or related types in `src/lib/types.ts`.
2. Update default settings or builder UI if the feature is configurable.
3. Update runtime logic in `workflowRuntime.ts` and helper logic in `workflowUtils.ts`.
4. Add server validation if clients can persist the new field.
5. Cover the behavior with workflow tests.

### Add a New Task Type

Task types are owned by workflows. Add or update a workflow in settings, make sure it has a `taskTypeIds` mapping, and verify the task type appears in creation flows. Use helpers in `src/lib/appSettings.ts` to normalize task type IDs and labels.

### Change Deadline Behavior

Update `src/lib/deadlinePolicy.ts` first, then verify:

- open/closed task filtering;
- audience selection;
- notification ID stability;
- receipt preservation;
- cron behavior in `api/cron/deadline-reminders.ts`.

### Change Daily Report Behavior

Update `src/lib/dailyReportWork.ts`, `src/lib/dailyReportScheduler.ts`, and relevant report policies. Verify that manual edits are preserved and exempt roles remain exempt unless the requirements intentionally change.

## Known Operational Constraints

- Background deadline and daily-report automation requires the server cron endpoint and a configured scheduler. The browser-only app does not run unattended jobs after all browsers are closed.
- Drive mode depends on Google OAuth, Drive API, Picker API, and the user's selected root folder.
- Neon mode depends on `DATABASE_URL` and server API availability.
- Local mode is browser-specific and should be treated as offline browser-local data unless migrated to shared data.
- Manual account passwords are stored as hashes in app settings; private fields must remain server-only in shared mode.
